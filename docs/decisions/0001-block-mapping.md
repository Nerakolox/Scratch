# ADR-0001：Paper 与 Canvas 的 Block 映射

- 状态：已采纳
- 日期：2026-11-10

## 背景

同一份内容需要同时支持：

- Paper：连续书写，跨段落选择、回车拆分、Markdown 快捷输入；
- Canvas：每个可变卡片必须对应稳定内容，拖动/连线/分组不复制正文。

候选方案：

1. **每个 Block 一个 Tiptap 实例**，Paper 用列表堆叠。
   - 优点：映射直观，每块独立编辑。
   - 缺点：跨块选择/删除/回车行为不自然；块之间空白与光标移动需要大量自定义；当块很多时为每个块常驻编辑器成本高。
2. **一个 Tiptap 文档 + 顶层节点稳定 ID**，每个顶层节点就是一个 Block。
   - 优点：原生编辑体验、IME、Markdown 输入、撤销；Block 粒度清晰；Canvas 卡片只需引用 ID。
   - 缺点：空段落、回车拆分重复属性、粘贴多段等情况需要插件修正。

## 决策

采用方案 2：

- `BlockIds` 全局属性 + `appendTransaction` 为顶层节点分配/去重 `blockId`。
- `syncPaperDocument()` 将文档顶层节点映射为 Block/顺序；空段落不新建 Block。
- Canvas 卡片不保存正文，只保存 `blockId` 与尺寸；预览从 DocumentService 读取。
- Canvas 卡片编辑使用单个节点的独立 Tiptap 浮层；Enter 为 hard break，关闭时如有多节点则拆分为多个 Block。

## 后果

- 只需要维护一个 Paper 编辑器实例，性能与输入体验稳定。
- 回车会自然地产生新 Block（一段一个新块），Canvas 会为新块创建卡片；这是有意的模型行为，并通过 ID 去重避免重复卡片。
- 列表/引用/代码块等复杂节点同样作为单个顶层 Block，Markdown 导出与画布卡片保持“一个顶层节点 = 一张卡片”。
- 如未来需要“一个列表拆成多张卡片”，需要引入更细粒度模型，v1 明确不做。
